# Synthetic collector

This Node entry point prepares contract-v1 ingest requests in memory. In fixture mode it has no sender, credentials, file input, URL-fetch option, mail intake or model integration (live reading and sending are described under the Boneo reader and the Bjurfors reader below). Its only executor produces authored fictional observations at `https://example.invalid`. Pending and disabled candidates have no executor and no live coverage.

Build with `vite build --config tools/house-scanner/vite.config.ts`, then run `node .house-scanner-build/collector.mjs`. The default mode is fixture and dry. `--source` can demonstrate permission rejection, but cannot enable a real source. `--mode` accepts only `fixture`.

Replay inputs are explicit: `--at`, `--run-id` and `--batch-id`. Defaults are fixed for reproducibility, not fresh publication IDs. Use the same options only when replaying the same run; assign new UUIDs for a distinct run. The fixture policy review window is fixed and expiration fails closed. No request is signed or sent; this output cannot establish server acceptance or activation.

The planner accepts up to 20 profile projections, uses enabled-profile geography/type unions, and reports requested price caps and gaps. It keeps numeric restrictions local because native filter semantics remain unverified. It includes unknown-price and upcoming paths explicitly. Partitions are planned, never claimed completed. No household, actor or recipient fields enter ingest requests.

A run has a 1000-observation ceiling, a stage request holds at most 100 observations and fixture requests have a 256 KiB ceiling. Source identity includes source ID, source listing ID and episode. Prices compare only within that identity, in observation-time order. Equal-time contradictions and explicit price conflicts break comparability, as do unknown prices. Repeated known values retain the latest meaningful previous price. History begins at the first supplied observation; this utility does not claim complete historical pricing.

Static checks cover syntax, types and bundling. Behavioral, permission-denial and replay verification remain pending user authorization. Keep generated `.house-scanner-build/` output ignored and out of Pages assets.

## Before a live run

Count the homes the household can see against the 1500-listing ceiling of `hs_household_snapshot` and the contract, and keep a
margin of 100: above the ceiling the snapshot raises for every member. A new source adds hundreds of homes in one run.
The full rules, including how to recover, are in `instructions/house-scanner.md`.

## Boneo reader (pending source)

`boneo-parser.ts` turns a public Boneo search page into contract observations from the embedded `__NEXT_DATA__` JSON. `live-reader.ts` is the guarded fetcher, shared with Bjurfors: pacing, caps, stop rules, run memory and the listing page phase live there once, and `robots.ts` parses and applies `robots.txt`. `live-run.ts` turns a run into begin, stage and publish requests and writes the coverage note. `page-read.ts` holds what both parsers share: the page result types, number helpers and the house-number rule for position precision. `source-adapters.ts` holds what differs per source (search URL, request headers, page readers, hosts). The registry entry is `pending`, not approved: approval is an operator step in the database, so nothing here publishes anything. The household owner chose to read public pages for personal use at their own judgment; that is recorded in the policy rights basis and is not a reuse license.

Live use needs all three flags: `--live --source=boneo --confirm-personal-read`, Without them the CLI refuses and stays fixture-only. `--mode live` is still rejected. A live run reads robots.txt first and refuses a disallowed path, sends `HouseScannerPersonalReader/0.1 (private household tool)`, makes one request at a time and waits between 1 and 2 seconds after each response before the next request (`MIN_INTERVAL_MS` 1000 and `MAX_INTERVAL_MS` 2000; each gap is drawn at random per request so a run does not hit the site in lockstep, a slow site slows the run, and the random source is injectable for tests), reads at most 40 pages per partition (25 results per page) and makes at most 600 requests per run including robots.txt. It sends no cookies and handles no login or CAPTCHA. Any non-200 (including 403 and 429), redirect, network error, timeout or page without embedded data on a search page stops the whole run with no retry. A page without embedded data is failed coverage, not an empty result. Output is counts, statuses and partition names; listing values are never logged, saved or printed, apart from the ids and two facts in the run memory below.

### Collector bounds, pre-filter and sending

The collector fills the shared catalog and does not read household profiles. Its bounds are constants in `prefilter.ts` (`COLLECTOR_BOUNDS`, `COLLECTOR_MUNICIPALITY`): Göteborg, apartments only, at least 60 m², known asking prices from 2,000,000 through 6,000,000 SEK, any room count. Before staging, an observation is dropped only when a known, undisputed fact is outside them. Unknown or conflicting values always pass, an absent price is unknown and bounds are inclusive. The summary prints `droppedByReason` counts only. The run ceiling is applied before this filter. Households filter the catalog with their own saved criteria in the app. `--profiles` is still accepted and ignored so older run scripts keep working; the begin request no longer carries profile versions.
After the filter, each kept listing's own page is read on every run (same guards, same 1 to 2 second gap, robots check on the exact path) for balcony, terrace, glazing and the floor, at most 500 pages per run. `property_detail.field_property_balcony` and `field_property_terrace` give `outdoor`: both true is `both`, one true is `balcony` or `terrace`, anything else is unknown, never `none`, because the broker may leave a box unticked. `glazed` is `true` only when `property_detail.body` says a glazed balcony, terrace or conservatory in Swedish ("inglasad balkong") and not "ej inglasad"; otherwise unknown. The text is matched and dropped. The same page gives the gallery from `property_detail.property_images[]`: up to four `Other` images in page order become the photo and three more, and the first `Planlösning` image is the floor plan. Only the `resize_image` file name is kept (a name that is not a plain file name is skipped); photos are rebuilt on the search page's `550x366` style and the plan on the larger `1650x1100` style the listing page itself uses. A listing page that returns a non-200 other than 403 or 429, has no embedded data or has an unexpected shape falls back to run memory (below) or, without an entry, leaves that listing's page facts unknown and is counted in `detailFailed`; 403, 429, a network error or a timeout ends requests to the source, and the listings not yet read fall back to run memory. Listings past the 500 page cap or the request cap fall back the same way; those without an entry, and those disallowed by robots.txt, count in `detailSkipped`. The summary prints `detailRead`, `detailCached`, `detailFailed` and `detailSkipped`. Lift and build year are not collected.

### Floor rule (both sources)

`groundFloor` is `false` when the floor number is 2 or higher, because that is above ground under every numbering convention. It is `true` only for an explicit marker (`BV`, `bottenvåning`) or the number 0. Floor 1, a missing value and anything unparseable stay unknown (`null`), since floor 1 can be ground level or one above it. The rule is in `floor.ts`. Boneo reads `property_detail.field_floor` (a string such as "3") and Bjurfors reads Våningsplan ("3 av 5"). Both policies allow `groundFloor`, and the Boneo policy is now revision 4, so the operator re-approves it.

### Run memory and pacing

A live read keeps one small JSON file, `house-scanner.cache.json` in the current directory (the `house-scanner.cache*.json` pattern is gitignored). `--cache <path>` picks another file. The file holds `version`, `lastLiveRunAt` and, per listing id, `readAt` and the facts that listing's page supplied. For Boneo that is `outdoor`, `glazed`, `groundFloor` and the image file names (`photoKeys`, `planKey`). For Bjurfors it is also `lift`, `propertyType`, `tenure`, `status`, `baseFeeSek`, `askingPriceSek`, `livingAreaM2`, `rooms` and the home's `latitude` and `longitude`. Entries hold ids, small enums and numbers only: no titles, street addresses, URLs or page text. A Bjurfors id is the listing path, which does name a street, and the coordinates locate the home, so keep this file out of version control like the profiles file. The summary never prints the contents.

- Every kept listing's page is requested on every run; the memory is only the fallback for a page the run did not read (failed, past a cap, or after a stop). A remembered entry under 30 days old fills only the facts the list left blank, and is counted in `detailCached`. It never holds a bid. Each good read replaces the listing's entry; failed or skipped pages are not remembered.
- When a source has more kept listings than the page cap, listings never read come first, then listings in bidding, then the oldest reads, so the ones left out are the most recently read and the next run reads them first.
- A live read refuses to start when the last one began less than 6 hours ago (`MIN_RUN_INTERVAL_MS`). It exits 1 before any request and prints the time left. `--force` skips this check. The start time is written right after the configuration checks and before the first request, so a run that fails or stops still counts.
- Entries older than 30 days are dropped on save, and the file keeps at most 5000 entries. A missing file is empty memory. A corrupt, wrong-version or oversize file (over 2 MiB) is treated as empty, reported as `cacheReset: true` in the summary and replaced on save. Deleting the file also lifts the 6 hour wait, as does `--force`.
- Saving writes a temp file next to the target and renames it, so a failed write leaves the previous file intact. If the final save fails the summary shows `cacheSaved: false`.
- Fixture mode never reads or writes the file, and `--cache` and `--force` are rejected without `--live`.

Sending needs `--send --confirm-send` on top of the live flags, and these environment variables:

- `HS_INGEST_URL`: `https` and ending in `/functions/v1/house-scanner-ingest` (`http://localhost` is allowed for a local stack).
- `HS_INGEST_KEY_ID`: the issued key id.
- `HS_INGEST_SECRET`: at least 32 characters. It is never printed or logged.

Requests go out in order (begin, stage in batches of at most 100, publish), each signed with HMAC-SHA256 over the method, path, timestamp, nonce and body digest, as the function verifies. The first non-2xx response, network error or timeout stops the run. Nothing is retried, because a retry would need a new nonce and the first attempt may have landed; the printed status tells the operator what to check. A stopped or truncated source run still publishes `partial` or `failed`, never `success`. The summary prints status codes and counts only and exits 1 when delivery stopped.

What was confirmed on 13 October 2026 from one search page and one beyond-the-end page:

- The page embeds `props.pageProps.listData.pData` and `count`. `count` is the total result count: `?page=2` kept `count` and returned no items.
- Price fields are numbers and the other-currency field was `SEK` where set. SEK is inferred, and any other currency makes the price unknown with a conflict.
- Coordinates are `{lon, lat}`, as numbers in most items and numeric strings in one. Precision is not stated, so it is recorded as `approximate_area`.
- The status field held `Till salu` on every returned item. Facet labels list `Kommande`, `Kommande-light`, `Removed from API` and `Såld`, and the facet counted upcoming homes that the default view did not return.

Unproven, and recorded as gaps in the registry entry:

- Page size and multi-page ordering. The page query is accepted, but no result set larger than one page was seen, so coverage is never reported complete and a run publishes `partial` or `failed`, never `success`.
- How to query upcoming inventory, and whether listings without a price appear in the default view.
- The municipality level path. Only the district path was observed; the municipality path is derived by dropping its last segment. A wrong guess fails as a page without embedded data.
- Houses (the apartment path segment is the only one known), municipalities other than Göteborg, and whether `created_date` is stable enough to serve as an episode across relistings.
- The `field_status_id` meanings other than `Till salu`, taken from facet labels only.

Fixtures under `fixtures/boneo/` are synthetic: invented addresses, prices and ids in the observed key shape, with case-colliding keys, a missing price, an upcoming status, a null coordinate, a non-active item, an off-origin link and a page with no embedded data. No real listing data or captured page is committed.

## Bjurfors reader (pending source)

Same guards and the same CLI as Boneo, with `--source=bjurfors`: `--live --source=bjurfors --confirm-personal-read`. The registry entry is `pending` at revision 1, executor `bjurfors-personal-read`, retention 14 days. The owner reads public search pages for personal use at their own judgment, on the same basis as Boneo. robots.txt for www.bjurfors.se (checked 16 October 2026) allows everything except `/globalassets/ragnar/`, `/contentassets/*.pdf` and one office path. The reader still checks the exact path of every request.

`bjurfors-parser.ts` reads server-rendered HTML. The search page has no embedded JSON, so the parser matches the card markup. Without ordinary `Accept` and `Accept-Language` headers the site answers 200 with an empty body, so the reader sends `text/html,application/xhtml+xml` and `sv-SE,sv;q=0.9,en;q=0.8` beside the honest user agent. An empty or tiny body, or a page without the results list, is failed coverage (`no-results-list`), never an empty result.

- Search URL: `/sv/tillsalu/vastra-gotaland/goteborg` and `?page=N`, 24 cards a page. Göteborg is the only municipality supported. The one search lists apartments and houses.
- Total and paging: the heading `<strong>N</strong> bostäder till salu` is the total (893 on 16 October, 38 pages), so a read ends when the cards received reach it. A page past the end shows an empty list with the same total, which is reported as truncated before the total (`empty-page-before-total`). The total can fall while a run reads as homes sell, so only a page's own cards are checked against it. A full 38 page read plus listing pages fits the 40 page, 1000 observation and 250 request caps.
- Card: `h3.c-object-card__heading > a.c-object-card__link[href]` with `span.c-object-card__city-area` (district, municipality) and `span.c-object-card__address` (street and number, used as the title). `li.c-object-card__meta` cells are recognised by unit: `62 kvm`, `217+40 kvm` (living plus secondary area, inferred from one house), `2 rum` or `2,5 rum`, and `3 250 000 kr`, which is missing on about half the cards. Type and tenure are not on the card. Tags are not read.
- Photo: the `img` src is a 16 by 24 placeholder. The photo comes from `<picture><source data-srcset>`, validated to the exact `/cdn-cgi/image/format=auto,fit=crop,width=320,height=480,quality=80/contentassets/<32 hex>/<name>.jpg?v=<digits>` shape on the same origin. The browser loads it and it is valid for 7 days. One image request without a Referer answered 200 with an avif.
- Identity: the listing path after `/sv/tillsalu/` is `sourceListingId` and the episode is the constant `listed`, because the cards carry no id or date. A relisting of the same home is not told apart. A card that links outside the for-sale listing path, such as a project page, is skipped.
- Pre-filter: area, rooms and price come from the cards, so the pre-filter runs on the cards and only kept listings get a page request. A card does not carry the property type, so houses pass until their page is read; the pre-filter then runs again with the page's type, area and price.
- Listing page: one `RealEstateListing` JSON block (price in `offers.price`, availability, `geo`, floor size, rooms) plus definition lists. The reader takes Utgångspris or the offer price, Boarea (fallback floor size), Antal rum or Rum, Avgift or Avgift/hyra, Typ, Upplåtelseform (Bostadsrätt is cooperative, Friköpt or Äganderätt ownership, Hyresrätt rental), Våningsplan (floor rule above), Balkong and Hiss. Only `Ja` is a fact for Balkong (`balcony`) and Hiss (`lift`). `Nej`, a missing row or anything else is unknown, because it reads like an unticked box. `InStock` is available and `PreOrder` upcoming (inferred). A missing or non-numeric value is unknown, never zero. Glazing is not collected. Descriptions, seller details and all other text are read past and dropped.
- Gallery: the listing page's `data-modaldata` JSON gives up to four photos and the first floor plan (`floorPlans[].originalUrl`). The home's photos, its plan, the agent portrait and the area pictures share one `/contentassets/<32 hex>/` folder, so the reader takes the `allImages` run before the first captioned image (the portrait and area pictures carry captions; the home's photos did not on the page checked 23 October 2026). Run memory keeps the `/contentassets/<hex>/<name>.jpg?v=<digits>` keys, and the adapter rebuilds them through the site's resizer: `fit=crop,width=658,height=480,quality=90` (its landscape gallery size) for photos and `fit=scale-down,width=1265,quality=90` for the plan.
- Coordinates: from `geo`. Four of four listings matched an independent geocoder (Nominatim) within 12 m of the street address, so a title with a house number is labelled `address` and any other `approximate_area`. The sample is small.
- Operator steps: `node .house-scanner-build/collector.mjs --print-policy-sql --source=bjurfors` prints the approval SQL for the operator to run in the SQL editor. The ingest credential is issued per source, so Bjurfors needs its own key id and secret in `HS_INGEST_KEY_ID` and `HS_INGEST_SECRET` for its run. Boneo's policy must be printed and run again because its revision is now 4.

Fixtures under `fixtures/bjurfors/` are synthetic: fake addresses, values and ids in the same markup shape, with search pages 1 and 2, an empty page, a page missing its total, a blocked page, and listing pages with every field, with missing fields and with the wrong shape. No real listing data, captured page or image is committed.

## Erik Olsson reader (pending source)

`erik-olsson-parser.ts` reads two kinds of page. The first photo of each kept home is hotlinked from the broker's Cloudflare Images address (`https://imagedelivery.net/<account>/<image id>/<variant>`), shown by the viewer's browser with no referrer and never fetched or stored by the collector. The policy allows images from `https://imagedelivery.net` only.

- Search URL: `/municipalities/goteborg-166?tab=homes`, later pages `&page=N` (the adapter's `pageUrl` hook adds the page number to an address that already has a query). Göteborg is the only municipality supported, and the number in the path is the site's own id. The one search lists apartments, houses and villas.
- Cards are server-rendered with Chakra's stable class names: the page title carries the total (`468 bostäder till salu i Göteborg`), every card has a wishlist button, and sixteen cards make a page (about thirty pages). A card's paragraphs are the street (the title), `Type, District, Municipality`, `3 rum • 87.3 m² • 6 000 kr / mån` (a house reads `5 rum • 113 + 58 m² • 121 m² tomt`, a villa has no room count) and the price, or `Inget utropspris`, which is unknown, never zero.
- Pre-market homes (`Underhand`) show no street and have no link, so they are counted and skipped. They were ten of sixteen cards on the first page seen and three of sixteen on the second, so this is the largest coverage gap and is listed in the policy.
- Identity: the number at the end of the listing path is `sourceListingId`; the episode is the constant `listed`.
- Pre-filter: area, rooms and price come from the cards, so only kept homes get a listing-page request, as for Bjurfors.
- Listing page: the facts sit in the framework's streamed data (`self.__next_f.push` string chunks), as a `"home":{...}` object with a numeric id. The reader joins the chunks, finds that object by counting braces outside strings and reads livingSpace, monthlyFee, rooms, price (`startingPrice`), property type, tenure, `floor` and `elevator`, balcony and patio flags, status and the broker's coordinates. Balcony and patio are facts only when `true`; `elevator` counts only as `Yes`; a zero or missing price is unknown; coordinates are dropped when the broker hides the address. The photo is the first entry of `home.images` that is not a floor plan; its account comes from the `imagedelivery.net` address the page itself uses (the social preview image), and the adapter requests a 640 by 480 thumbnail variant, valid for seven days like Bjurfors photos. On one sample that variant loaded as a JPEG of about 39 kB, and `imagedelivery.net` serves no robots.txt (it answers 400). Descriptions, broker and nearby-place data are read past. Glazing is not collected.
- Operator steps: `node .house-scanner-build/collector.mjs --print-policy-sql --source=erik-olsson`, then a credential for this source (`hs.admin_issue_credential`), as for Bjurfors.

Tests use pages authored in `erik-olsson-test-pages.ts` (fictional streets and values in the same markup shape). The parser was also run once against the five pages fetched for the probe, which are not kept in the repository.

## Stadshem reader (pending source)

`stadshem-parser.ts` reads two JSON documents the site's own pages load. Nothing is parsed from HTML. Photos are hotlinked, and the policy allows images from `https://storage.googleapis.com` only.

- List: `https://stadshem.se/api/estates?per_page=100&orderby=published&order=desc&status[]=till-salu&status[]=snart-till-salu-kommande&page=N`. It answers `{ total, page, num_pages, estates, filter }`. One answer held all 94 homes on 17 October, so a run is usually one request; the adapter's `pageUrl` hook changes `page=` when `num_pages` says there is more. The list covers all of Sweden, so the reader passes the partition's municipality (a new `municipality` field of the read context) and keeps only that one; Göteborg is the only one supported. The rest count as skipped.
- Estate: `estateId` (letters, digits and sometimes an underscore) is the identity; `id` is `estate-<estateId>-<slug>`, and the public page is `https://stadshem.se/objekt/<estateId>-<slug>`, without a trailing slash (the slash form redirects, and the reader never follows redirects). Facts: `livingSpace`, `numberOfRooms`, `monthlyFee`, `price.startingPrice` (zero or `hidePrice` is unknown), `type` (`lägenhet` is an apartment, `radhus`, `hus` and similar are houses), `status.slug` (`till-salu` is available, `snart-till-salu-kommande` is upcoming) and the broker's `address.coordinates`, labelled address-level when the title has a house number.
- Record: the adapter's `detailUrl` hook sends the per-home read to `/api/estates/<estateId>` while the observation keeps the public page address. It gives `floorAndElevator.floor` (the shared floor rule), `elevator` (only `Yes` is a fact) and `baseInformation.tenure`. Balcony and glazing have no structured field and stay unknown. Descriptions, agent and association text are read past.
- Photos and plans: the record's `images.other` lists the photos in page order, the first being the list's primary image. The reader keeps the `sizes.medium` path of up to four of them and of the first `images.floorPlans` entry as keys in run memory, so a home read from memory keeps its gallery; the adapter's `imagesFor` rebuilds the addresses on `https://storage.googleapis.com`. A path off that host or outside `STADSHEM_IMAGE_KEY` is dropped.
- Operator steps: `node .house-scanner-build/collector.mjs --print-policy-sql --source=stadshem`, then a credential for this source, as for the others.

Tests use answers authored in `stadshem-test-pages.ts` (fictional streets and values in the same shape). The parser was also run once against the real list and record saved from the probe, which are not kept in the repository; that run found real ids with an underscore, now accepted.

## Lundin reader (pending source)

`lundin-parser.ts` reads two kinds of answer: the JSON list at `https://www.lundin.se/api/list?id=1`, which the site's own page loads and which holds every object the broker has (245 on 17 October 2026), and each kept home's public page. Photos are hotlinked from the same host (`/dc/<image id>.jpg`), and the policy allows that origin only.

- A run is `robots.txt`, the list, then one page per kept home (`/beskrivning/<Guid>/<slug>`, the observation's `sourceUrl`) under the shared guards: robots check, 1 to 2 seconds apart, at most 500 pages, with run memory as the fallback for a page that fails. That is about 30 to 100 pages a run.
- From the home page only image ids are read: the first four `figure.object-image[data-id]` inside `<section id="sectionimages">` (the six-photo preview, in page order) and the id in the `/dc/<id>.jpg` address of the first `figure.object-image-plan` inside `#section-planimages`. Each id must be a plain id. Photos are rebuilt with the list photo's size query (`mode=max&w=640&h=480&scale=down`) and the plan with a 1200 by 1200 box. A page without images keeps the list photo; a page with no canonical `/beskrivning/` link is counted as failed. Floor, lift, balcony and glazing stay unknown. The policy is revision 2 for this change, so the operator prints and runs its SQL again.
- Identity is `Guid`; the public page is `DescrUrl`, which must be `/beskrivning/<Guid>/<slug>`. Facts: `Price` (zero is unknown), `Rent` (the monthly fee), `Area`, `Rooms`, `Type` (`CMBoLgh` in any letter case is a tenant-owner apartment, `CMVilla` and `CMFritidshus` are houses; plots and new production are skipped), `Status` (`Till salu` is available, `Snart till salu` is upcoming; `Såld` is skipped).
- The list has no municipality. `City` and `ParentLocation` place a home in Göteborg (city Göteborg, or a district such as Innerstaden or Västra Göteborg) or Mölndal (city Mölndal, or `Mölndals kommun`). Anything else is skipped rather than guessed. Run against the saved answer: 90 Göteborg and 13 Mölndal homes kept.
- There are no coordinates, so the geocoder estimates a position for the homes that are kept.
- Operator steps as for the others: `--print-policy-sql --source=lundin`, then a credential for this source.

Tests use answers authored in `lundin-test-pages.ts` (fictional streets, values and image ids in the same shape); the parsers were also run against the saved real list and one saved home page, which are not kept in the repository.

## Husman Hagberg reader (pending source)

`husman-hagberg-parser.ts` reads one JSON document: `https://api.husmanhagberg.se/object/api/objects?ps=200&regX=G%C3%B6teborg`, the list the site's own search pages load. It answers `{ estates, count }`; `ps` is the page size and `regX` a text match on the name. One answer held all 143 matches on 17 October 2026 (485 kB). Photos are hotlinked from `https://media.husmanhagberg.se`, and the policy allows that origin only.

- A run is `robots.txt` of `www.husmanhagberg.se`, the list, and the public estate page (`https://www.husmanhagberg.se/estate/<objectReference>/`, about 420 kB) of each kept home under the shared guards: one to two seconds apart, at most 500 pages a run, with run memory as the fallback for a page that fails. A run is about 50 to 140 pages, roughly two to five minutes. The API host has no robots.txt (404), so the guard applies the site's rules to the list path; the estate pages are on the site itself. The site's robots.txt allows everything; its terms of use have no clause on automated reading and bar copying and spreading protected texts and images without consent.
- Identity is `objectReference`; the public page is `https://www.husmanhagberg.se/estate/<objectReference>/` (the `/sv/estate/<ref>/` form redirects to it). Facts: `startingPrice` (zero, missing or `details.advertiseOn.hidePrice` is unknown), `monthlyFee`, `livingSpace`, `numberOfRooms`, `address.municipality`, `estateType` (`HousingCooperative` is a tenant-owner apartment, `House` is a house with unknown tenure; `Cottage`, `CommercialProperty` and anything else are skipped), `statusId` with `showAsComing` (`ForSale` is available, a shown `TakenIn` is upcoming, anything else is skipped).
- Floor comes from `details.floorAndElevator.floor` for apartments, through the shared floor rule. Lift, balcony and glazing are not in the list and stay unknown.
- Estate page (`readHusmanHagbergDetailPage`): only image keys are read from `script#__NEXT_DATA__`. Photos are the first four `props.pageProps.estateDetails.images[]` whose `category` is not `Områdesbild` (area pictures); the plan is the first `estateDetails.plans[]`. A key is `<folder>/<mediaId>` from the entry's own `sizes.list2x.url`, which must pass the media host path check. The adapter rebuilds photos at `-672x448.jpg` (the list's `list2x`) and the plan at `-1410x940.jpg` (`full`). Run memory keeps the keys, never addresses. `estate.details.images[]` (with unpublished images) and all page text are not read. A home whose page is not read or has no photos keeps the list photo.
- Position is the broker's `address.latitude` and `longitude` (strings), dropped when the address is hidden (`details.advertiseOn.hideAddress`), and labelled address-level when the title has a house number. A hidden address also falls back to the area name as the title.
- Paging: no parameter was found. If the answer holds fewer homes than its `count`, the partition is reported truncated (`empty-page-before-total`), never complete.
- Only Göteborg is supported. The match is on text, and the broker's own municipality list counted 206 for Göteborg against 143 returned, so some homes may be missed; the reason was not checked.

### Estimated positions

Kept homes with a house number in the title and no source position are looked up on OpenStreetMap's Nominatim (`geocoder.ts`): honest user agent, 1.5 seconds apart, at most 60 per run, stop on the first error. Answers are cached in `house-scanner.cache-geocode.json` (gitignored by the `house-scanner.cache*.json` pattern): hits for 90 days, misses for 7. A matched address is stored with `precision: address` and `estimated: true`. A street-only match is stored as `approximate_area`; district or town results are not treated as houses. The database keeps every official neighborhood intersecting a 50 m browsing buffer around an address estimate or a 250 m buffer around a street estimate. These radii are assumptions for browsing, not measured accuracy or the extent of the whole street. Cards say “Near … (approximate)”; selecting any candidate area includes the home. Existing cached answers are reused, so this is not an extra lookup on every scan.


### Stored listings, saves and changes

The collector fetches source pages and sends signed begin, stage and publish requests. It does not download favorites or hidden IDs. The database owns those records independently of collection. The collector bounds decide what is collected. An apartment a run staged before stays collected after it moves outside the area or price bounds (homes of other types are dropped and age out): the run memory file keeps its source and listing ID for 30 days after it was last staged, so its price and status stay current. Listings form one shared catalog identified by source, source listing ID and episode ID; another source or a new episode is a separate record. Each household sees catalog listings while the source policy is current and they are within retention and pass its saved criteria (`hs.fails_hard_rule`), plus any it favorited, noted or hid. Manual links live in a separate table owned by one household. Cross-posted copies are folded by the app without merging database rows.

Publishing is atomic. An unchanged home keeps its ID, favorites, notes and hides (hides are shared by the household). Failed sources preserve their previous data. Each publish also says whether the search was read in full (`fullRead`) and which homes were seen (`seen`, before the collector bounds); a home missing from two full reads in a row is marked `delisted_at` and leaves normal browsing, and a later sighting unmarks it. Expired homes leave browsing but stay stored; nothing deletes them. Source display restrictions still apply to what can be shown.

The local detail cache stores small facts for seven days. A separate cache holds address lookup answers for 90 days and misses for seven. These caches reduce requests; they do not replace database history or carry user saves/hides.

The publisher compares normalized JSON through `hs.observation_content`. It ignores refresh/publication timestamps, coordinate observation times, photo observation/expiry times, evidence IDs/times and viewing schedules. A meaningful difference increments `revision` and appends a row to `hs.observations`; an ordinary refresh updates the current observation and last-check time without adding a revision. This is a content comparison, not a field-by-field change log in the UI.

| Field | Meaning |
| --- | --- |
| `first_seen_at` / `firstSeenAt` | Server time when this record was first discovered. Stable across refreshes. Historical backfill uses the first retained observation only when the complete revision history remains; otherwise it stays unknown. This is not the broker's publication date. |
| `last_changed_at` / `lastChangedAt` | Server time of the latest meaningful content revision. Refreshes, new viewing times and retention cleanup do not advance it. |
| `last_checked_at` / `lastCheckedAt` | Server time when a newer source observation was accepted, whether its meaningful content changed or not. |
| `observed_at` / `observedAt` | Observation time supplied by the collector. Used for ordering, stale-data checks and retention. |
| `first_seen_run_id` | Run that introduced this source listing episode. It is compared with the latest published successful or partial run of that same source to derive `isNew`. |

The UI's New badge means discovered in that source's most recent published scan. Opening, favoriting or hiding it does not clear the badge; the next successful or partial scan of the same source does. A later run of another source does not. The Latest filter offers that group and homes first found within 1, 3 or 7 days. These controls use discovery time rather than treating refreshed homes as new.

For a comparable asking-price change, such as 4,700,000 to 4,500,000 SEK, the same listing's `value.facts.askingPriceSek` becomes 4,500,000, `previous_asking_price` becomes 4,700,000, and `previous_price_observed_at` records the earlier observation time. The snapshot exposes `previousAskingPriceSek`; cards and details strike through the earlier price and show a direction arrow. Unchanged scans retain that comparison. A further change replaces the comparison with the immediately preceding price; observation rows retain older changes subject to retention. Unknown or disputed prices break comparability and clear the previous-price comparison. Prices are never compared across sources or listing episodes, and policy/retention rules can hide historical prices.
